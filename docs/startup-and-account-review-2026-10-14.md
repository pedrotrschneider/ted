## Startup investigation — deferred backlog

This review inspected current code and the prior measured traces; it did not launch new media, create watch events or interrupt the running deployment. Baseline evidence is in IMPLEMENTATION.md and `.devbox/test-evidence/t5c-source-cache-2026-10-14/`. Last investigation: 9/9 add-on requests succeeded; exact-file fresh preparation took 7.879/6.505/2.728 seconds, of which RD resolution was 3.297/0.911/1.549 seconds. These are preparation timings, not end-to-end native first-frame timings. A previous warm session prepared in 9 ms. Historical engine-ready timings preceded the network correction and must not be presented as today's baseline.

### Ranked opportunities, not implemented changes

1. **Remove duplicated RD reads within one preparation.** `Inventory.resolveSelection` in `internal/realdebrid/addon_source.go` calls `AccountID`, fetches torrent detail to identify the selected file, then calls `Client.ResolveFile` in `internal/realdebrid/playback.go`. ResolveFile calls AccountID and fetches that torrent detail again before unrestricting the matching file link. In the ordinary ready-file path this repeats two serial API reads. Investigate passing the just-validated account/detail (including selected-file link mapping) through a narrowly scoped internal adapter operation, retaining hash/path/size/status/link-shape checks and the final unrestrict filename/size validation. Keep account credential scope pinned and source mutation locks intact. This can benefit a genuinely cold play and background preparation without a persistent validation cache. Request-count reduction is established by code; latency savings are not yet measured.
2. **Make the chosen add-on result available before unrelated slow providers finish.** `internal/addons/store.go` prioritizes favorites/continuations but still waits for every lookup worker before publishing results. A fast eligible result can therefore wait behind an unrelated provider. Investigate incremental result delivery or an explicit preferred-provider-first response followed by background completion. Preserve the complete/partial/failure distinction, deduplication, preferred source identity and explicit selection; never let late results silently change the selected release. The twelve-hour frontend cache already avoids most repeated lookups. The now-implemented shared add-on account also permits investigating server-side reuse of normalized discovery results, but account-owned source handles/playback sessions must remain separately authorized. No new endpoint or cache is approved by this review.
3. **Overlap player initialization with session preparation.** `TedPreparingPlayer` constructs the actual player only after a validated session arrives; `TeddyPlayer` creates a new Player and then loads settings/local language preferences and configures it before opening media. Measure engine creation, local initialization, request-to-file-loaded and file-loaded-to-first-rendered-frame separately. If initialization is material, consider creating the idle engine on explicit Play while TED prepares the source. Never open unvalidated media or produce reports before a session exists; cancellation must dispose the engine. Do not assume CPU decoding is responsible for network/open/seek wall time.
4. **Measure the remaining range-request critical path.** Startup already overlaps header/tail reads, validates the canonical first/last 4 KiB fingerprint, streams the remainder of the 2 MiB head progressively, and disables the initial mpv cache-fill gate. The entire 128 KiB tail still completes before publication. Inspect traces for unused continuation transfers or avoidable additional header/index/seek requests, comparing cold playback at zero and at a resume offset. Reducing read-ahead or tail coverage without this evidence may add more round trips and make startup worse. Do not relax file identity, range/ETag checks, original-language preferences or placeholder protection.
5. **Treat alternative CDN routing as an unresolved experiment.** The RD-issued `sao1-4` media host is IPv4-only and showed intermittent TCP stalls; the official dual-stack São Paulo base host served one matching diagnostic file quickly. That does not establish an official production alias/rewrite contract or performance across files. No CDN hostname rewriting or account setting change is proposed as a quick fix. Controlled comparisons would need same-file repeated trials and preserved identity validation before a separate decision.

Lowest priority for the current request: persistent cross-session media-byte caches (owner previously deprioritized repeat-play improvements), larger initial buffers, and broader speculative prefetch. Current next-episode prefetch is accepted and should remain bounded to its selected matching release.

A future measurement pass should distinguish source-cache hit/miss, preferred-source lookup, RD API round trips, validation, session publication, player initialization, first rendered frame and actual advancing playback. Compare unprepared cold play, prepared details Play, and prefetched Next under the same file/source/resume conditions. Measure a distribution rather than infer a guaranteed improvement from one fast trial. Recommended first experiment: duplicated RD API reads; do not implement until separately authorized.


## Account decisions now implemented

The canonical contract is [PROJECT](../PROJECT.md), not the former proposal/order in this file. Server-wide administrator Stremio discovery is separate from personal two-way history links. The authorized migration reused native_tester's external account in both roles without coupling future disconnect/replacement. Joint memberships provide read-only colored watch projections, no nesting or history merges. Shared external history accounts remain allowed with an indirect-sync warning. Badges stack at the **top right**, using expanding watched/total pills and complete checkmarks.

Teddy's OS-backed multi-profile bundle preserves servers/profiles, but only the selected profile authenticates. Profile choice appears every startup. Switching pauses/checkpoints transfers and preserves scoped data; explicit Sign Out fences work and purges only that profile's credentials, owned files, caches and pending reports. It does not affect server history, other profiles or installation identity. The earlier proposal to continue inactive downloads is superseded.

Browser-only logout, Keychain retry/error handling, first-visible Home focus and profile chooser UI have also been corrected. Their verification and the two settings-default discrepancies discovered in the handoff audit are recorded in IMPLEMENTATION; this performance review is not a second execution backlog.
